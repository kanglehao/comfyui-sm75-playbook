# 11 · 工作流修复与验证

> 这一篇的核心是一句话：**"文件存在"不代表"能加载"，"能加载"不代表"能执行"。**
> 我们在这三档之间翻过车，代价是 661 处改动里漏了 109 处。

---

## 一、模型下拉值必须是反斜杠

### 规则

`/object_info` 给的候选长这样：

```
MiniMax-H3\minimax_h3_fl2va_pruned_int8_convrot.safetensors
```

工作流里也必须写**反斜杠**。写成 `MiniMax-H3/xxx.safetensors` 或裸文件名 `xxx.safetensors`，
**前端精确字符串匹配不上 ⇒ 输入框变红 ⇒ 报错**，哪怕磁盘上文件确实在。

### 为什么容易漏

写脚本批量替换时，直觉是用 `os.path.exists()` 判断模型是否存在。
这个判断**永远是错的**——它只能告诉你磁盘上有文件，不能告诉你前端能不能匹配上。

### 正确的校验方式

```
✅ 拿运行中实例的 /object_info 候选池做精确字符串比对
❌ os.path.exists()
❌ 自己跑一遍节点加载器生成的表（和前端用的候选池不是同一份）
```

我们曾经写过一个验收脚本，用 `os.path.exists` 判定，22 处写成 `/` 全部"通过"，
一打开全红。**这个错法很隐蔽，因为脚本会给你绿灯。**

## 二、子图的 widget 值存两份

用子图（subgraph）封装的工作流，下拉值有**两份**：

| 位置 | 说明 |
|---|---|
| `definitions.subgraphs[].nodes[].widgets_values` | 子图**定义内部** |
| 实例节点的 `widgets_values` | 子图**实例**上的副本 |

**前端读的是实例那份。** 只改内部等于没改。

更麻烦的是：实例节点的 `type` 是**子图 UUID**，不是节点类型名。
如果你的批量脚本按"跳过未知类型"处理，就会把整个实例跳过。

### 正确做法

判断实例的下拉值时，要用**内部所有节点候选池的并集**来匹配。

我们第一批 552 处改完，抽检才发现漏了 109 处——全是子图实例里的副本。

## 三、验证工作流"真的能用"的五步

别再只看文件存在。按顺序做，每一步都是独立的判据：

| 步骤 | 判据 | 工具 |
|---|---|---|
| 1 | 节点类型在运行中实例里存在 | `/object_info` 的 key 集合 |
| 2 | 下拉值能精确匹配候选池 | `/object_info` 的候选数组 |
| 3 | 浏览器能加载，无弹窗 / 无 MissingNode | `app.loadGraphData()` |
| 4 | 能转成后端 prompt | `graphToPrompt()` 成功且有节点数 |
| 5 | 必填输入都有连线 | `/object_info` 的 `required` 字段 |

⚠️ **新版前端 `app` 要等约 40 秒才就绪**（6000+ 节点注册）。
早于这个时间探测会得到 `hasApp: false`，别误判成加载失败。

### 用浏览器做验证的最小写法

```python
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    # 直接复用系统 Edge，不用下 chromium
    browser = p.chromium.launch(channel="msedge", headless=True)
    page = browser.new_page()
    page.goto("http://127.0.0.1:8188")
    page.wait_for_function("window.app && app.rootGraph", timeout=60000)
    page.evaluate("app.loadGraphData(%s)" % json.dumps(workflow))
    ok = page.evaluate("!!(app.graphToPrompt && app.graphToPrompt().output)")
```

> 注意：系统默认的 `python` 可能没装 playwright。用一个装了它的解释器，
> 别在这上面浪费半小时。

### 批量体检

如果工作流库有几百个文件，写个脚本跑全量普查：
单条约 0.7 秒，两百多个文件四分钟出报告。

**改完工作流想确认没搞坏，直接跑全量普查，别抽检。** 抽检就是上面那 109 处的来源。

## 四、批量修改的纪律

我们做过几次上千处的批量改（斜杠修正、路径重写、去重清理）。能活着回来的前提是三条：

### 1. 先全量备份，且备份要能一键回退

不是"复制一份到某处"，而是**写一个能真正跑通的回退脚本**，
并且验证它真的能扫到那些文件。

我们踩过：回退脚本是就地扫描 `.bak_20261019`，后来备份被搬到别的目录，
**旧脚本会静默扫到 0 个文件**——它不报错，只是什么都没做。

> **回退脚本必须在改动后立刻试跑一次。** 能扫到 N 个、N 等于你改的数量，才算合格。

### 2. 改之前先量一遍"应改数量"

先用只读脚本统计出所有命中项，人工确认这个数字合理，再执行。
否则你不知道自己漏了还是改多了。

### 3. 改完必须用同一套判据复量

数量应该等于预期。多出来或少了，都要查清楚再继续。

## 五、别静态扫 `custom_nodes` 判断"节点够不够"

新版节点包用 `io.ComfyNode` + `node_id=` 注册，**静态扫目录会漏判**。

而且用 ComfyUI 自己的加载器判断时，必须**先装 PromptServer 桩**，
不装会把几十个包全判成加载失败——你会以为环境坏了，其实是判断方法坏了。

**最可靠的判据永远是：运行中实例的 `/object_info`。**

---

## 六、一次典型修复的完整动作清单

以"某个工作流打开就报红"为例：

```
1. 拉 /object_info                                    ← 不动文件，先拿到真相
2. 逐项比对节点类型与下拉值（精确匹配，注意反斜杠）
3. 只在"确实不匹配"时才改，改前备份整个 workflows 目录
4. 改完抽 1 个文件，浏览器 loadGraphData 验证
5. 跑到 graphToPrompt 成功，才算改对
6. 全量普查，确认没有引入新问题
7. 留下变更记录：改了什么、为什么、怎么回退
```

第 7 步不是形式主义。三个月后（或者换台机器之后）你会需要它。
