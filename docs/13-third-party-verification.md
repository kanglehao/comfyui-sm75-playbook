# 13 · 第三方复现报告（ComfyUI 0.43.2 / 单卡 2080 Ti）

这份文档收录**别人**按本仓库的步骤跑出来的结果，以及他挑出的问题。
记在这里有两个原因：一是我错了的地方要留痕；二是他的机器条件和我不同（单卡 vs 双卡），
他的数字本身就是另一组有用的参考。

> **数据归属**：下面的计时是对方在自己机器上测的一手数据，**本仓库没有复验**。
> 我复验的是"代码和文件层面能不能对上"——见后面「逐条核实」。

## 实测数据

768×512 / 56 帧：

| 轮次 | 配置 | 端到端 | MD5 |
|---|---|---|---|
| R1 | 4 步 LoRA（下载成 PEFT 命名，键一个没加载） | 491 s | `d4d93784` |
| R2 | 4 步 LoRA（`_comfyui_` 版本） | **163 s** | `cd777f0a` |
| R3 | 8 步 LoRA + 8 步（本仓库默认） | **427 s** | `ee9a7abd` |

稳态 19.4 s/it，首步 43.7 s（含冷启动），产物 h264+aac 双轨齐全。

**这组数字的用法**：R3 是他那台**无 CUTLASS 减速节点**的单卡基线。
`19.4 s/it` 和本仓库双卡的 `6.5 s/it` **不能直接比**——s/it 强烈依赖帧数、分辨率和是否双卡，
跨配置比 s/it 是错的判据，只能比端到端同一配置的 A/B。

R1→R2 那 328 秒的差，就是 [06-models.md](06-models.md) 里 `_comfyui_` 后缀那条坑的代价。
他把这一轮记下来，正好成了那个判据的实证。

### 第 1 条：我自己踩了自己的坑

他的原话是"它自己的示例工作流违背了它自己的核心结论"。机器核对：

```
顶层 148 实例 :  ["", 1344, 768, ..., "qwen3vl_32b_minimax_h3_nvfp4_awq.safetensors", ...]
内部 136 CLIP :  ["qwen3vl_32b_minimax_h3_int4_convrot.safetensors", ...]
```

空 prompt、1344×768、nvfp4 —— 三个全中。原因是生成脚本只遍历了
`definitions.subgraphs[0].nodes`，从没碰顶层实例节点。这是**规则写对了、执行没遵守**。

已修：`scripts/inject_accel.py` 现在强制两边一起写，写盘前做一致性审计，不一致拒绝输出。

### 第 4 条：比他说得更早

他说的是 0.43.2。我去查了 0.41.3（也就是本文档的基线版本），**同样不覆盖**：

- `comfy/ops.py:1071` —— 采样主干走 `quant_ops.ck.int8_linear(..., convrot=True)`
- `comfy_kitchen/tensor/int8.py:172` —— 反量化函数唯一的真实调用点，属于
  `TensorWiseINT8Layout.dequantize()`（显式反量化）
- `comfy/` 目录下搜 `dequantize_int8_convrot_weight` —— **零引用**

所以他观察到的"每轮只调用 1 次"和源码是对得上的：那一两次来自 LoRA 权重补丁。
补丁挂上了、日志干净、跑得也稳，但**原始故障点已经不在它管的范围里**。

这条是本轮最有价值的反馈，[docs/05](05-pitfalls.md) 已改写，
并新增 `scripts/check_patch_reach.py` 让每个人自己判，而不是听我说。

### 第 8 条：我接受降级表述

我原文写"只有 `fastvideo_fasth3_8step_v2_pruned_int8_convrot` 把 token_refiner 也量化了"。
他说本机 fl2va 也调到了一次。

我没有条件复现他的这一次调用（要跑一轮 + 打桩），所以**不去断言谁对**，
而是把结论改成不依赖这个断言：持续触发的是 fastvideo，但别的模型也会在某些一次性路径上调到，
区别只在频次。这样无论他说的那一次来自哪里，加固建议都成立。

## 他没有主张、但顺带说明的事

R1 的 491 秒，在他那是"下错了 LoRA 文件"的代价。这条经历反过来证明了一件事：
**LoRA 加载失败是静默的**。不报错、不警告，只是没生效。
所以验证 LoRA 有没有真正加载，不能看日志里有没有 ERROR，要么看字节数（格式判据），
要么比对换 LoRA 前后的端到端耗时。

## 我的解释与他的判断不一致的一处

他提到"`turbo_steps` 是 8，而内层写 6"。查过链路后，这个现象的解释和他想的不完全一样：

```
实例 value_2=8 → link 245 → PrimitiveInt(146).widgets_values[0]
             → ComfySwitchNode(144) → BasicScheduler.steps
```

`BasicScheduler` 里那个 `["simple", 4, 1]`（以及 `PrimitiveInt` 的 6）是**被连线覆盖的缓存值**，
不参与执行。执行用的是实例传下来的 8。

所以它不是"值不一致导致跑错"，而是"文件里躺着三个互相矛盾的数字，谁看都会误读"。
新生成的工作流里，`PrimitiveInt` 已和实例统一为 8；`BasicScheduler` 那个 4 仍是缓存，
**因为它被连线覆盖、改了也不影响执行**——但它确实会误导人，这一条算文档债。

## 如果你想贡献自己的复现结果

有价值的是这四样，其他都可以省：

1. **ComfyUI / kitchen / torch 的准确版本**（不是"最新"）
2. **同一配置、换 seed 的端到端耗时**（同 seed 会被执行缓存整段复用，2 秒返回、产物字节一致）
3. **产物 MD5**（证明不是缓存命中）
4. **`check_patch_reach.py` 的退出码**——它直接说明补丁在你那版上有没有用
